# 输出吞吐量（tok/s）指标补充

本目录支持[11月1日已收口日报](../../daily/2026-11-01.md)和[长期工作报告](../../REPORT-PROGRESS.md)的指标补充。所有数值来自已经包含在对应报告中的完成数据；没有新启动GPU实验、重新检查远端状态或合并11月1日15:01:27之后的采样窗口。原日报统计起止不变。

## 指标与时间分母

| 指标 | 公式 | 解释 |
|---|---|---|
| 总输出吞吐 T_out（tok/s） | `sum(成功且实际长度校验通过的正式请求output_len) / duration_s` | 四卡服务整体交付率；输出token才进入分子。 |
| 达标输出吞吐 G_out（tok/s） | `sum(成功且TTFT<=500ms、TPOT<=30ms的请求output_len) / duration_s` | 仅满足冻结研究门槛的输出，不代表门槛已是业务SLO。 |
| 请求有效吞吐（req/s） | `达标请求数 / duration_s` | 与tok/s分开命名。本次各负载成功输出均为128token，可将该值乘128得到G_out；输出可变时必须逐请求加总。 |
| 生成速率换算（tok/s） | `1000 / 平均TPOT(ms)` | 单请求生成耗时的倒数换算，不是T_out，不是逐请求速率算术均值。 |

`duration_s`采用每个正式窗口已经保存的完整计时，包含输入处理、到达间隔和末尾排空；不包含服务重启、加载、smoke和预热。本地拒绝没有输出，贡献0token，没有用计划请求数乘配置输出长度代替实测token。各轮先独立计算，再对同负载/配置三轮等权平均；均值范围不等于统计置信区间。

固定周期4req/s、每次128输出的计划输出率是512tok/s；系统实测约511tok/s说明它在该负载下交付了这些输出，不能据此推导最大容量。请求变慢但最终仍全部完成时，总token近似固定，吞吐可能接近，而TPOT/在途和达标输出明显不同。固定并发的历史主基准另列，不与固定到达率混合解释。

## 收录数据与验证范围

[throughput-summary.json](throughput-summary.json)保存：

- 夜间第二次独立执行的36个600秒正式负载窗口：逐窗实际成功token、完整计时、T_out/G_out、三轮聚合。
- 14时ABBA短诊断的4个240秒clean窗口：逐窗同一分母和公式，0个profile窗口混入。
- 既有30秒有效吞吐阶段的9个配置/到达率聚合：沿用原先已核验的27窗口summary，交叉核对其原生output_throughput与`成功数×128/duration_s`。该较早阶段本次未再遍历原始请求。
- 历史固定并发基准的C1/8/32参照：与原基准重叠，不计新实验。
- 全部采用来源的相对路径、文件字节数和SHA256。路径/hash标识私下保留的原件，公开派生JSON不包含原始请求正文。

40个夜间/短诊断原始请求文件的hash与保存摘要一致；逐请求检查了成功、拒绝、实际`output_len`与服务端`completion_tokens`一致。达标输出独立按逐请求TTFT/TPOT计算，并与原`good_requests`和`request_goodput`交叉核对。

原ABBA单请求微测每个block混合输出1和128，只有一个共享block计时。没有把其中一个子组的token除以整个block计时并标为其独立单流吞吐；该实验仍以首响应/TPOT比较为主。

## 复算一行示例

clean1-A：实际成功输出122,880token，完整计时241.25999395101098秒：

```text
T_out = 122880 / 241.25999395101098 = 509.33 tok/s
G_out = 21 × 128 / 241.25999395101098 = 11.14 tok/s
```

全部请求成功不等于全部按时完成；G_out保留了500ms/30ms研究门槛的有效性要求。输入处理、生成耗时、拒绝与总吞吐应共同评价，不能只凭T_out接近就断言两个状态一样快。
