# DeepSeek V4 Flash MTP 性能边界与瓶颈研究设计

日期：2026-10-30

状态：研究设计及书面 spec 已于 2026-10-30 获用户确认通过；Task 1～7 已执行验收，候选因TTFT超出门槛不保留，原四卡固定3步MTP服务已恢复。结果及可归因范围见 REPORT-MTP-BOUNDARY.md 和本轮 completion.json。

## 目标

在当前四张 RTX PRO 6000、TP=4、DeepSeek-V4-Flash 和 SGLang 0.5.23 环境上，解释 MTP 推测解码的收益来源与失效边界，并验证一个有证据依据的改进假设。

第一阶段交付一份“**MTP 性能边界与瓶颈报告**”，报告需要回答：

- 当前 MTP 加速主要来自哪些执行阶段；
- 并发度和上下文长度增加到什么范围后，MTP 的净收益明显下降；
- 草稿生成、验证、通信和调度分别能测到什么程度；
- 哪一个改进假设最值得继续实现；
- 改进前后的结果是否可复现。

## 当前证据和研究假设

已有三轮 TP=4 原始结果显示：

| 并发 | 普通解码输出 tok/s | MTP 输出 tok/s | MTP/普通 |
|---:|---:|---:|---:|
| 1 | 101.22 | 188.39 | 1.861x |
| 8 | 588.83 | 758.18 | 1.288x |
| 32 | 1288.76 | 1321.95 | 1.026x |

512/128、并发 8 的 MTP `accept_length` 约为 2.88；并发 1 和 32 也接近这一数值。源码审计显示该字段由 benchmark 读取 `internal_states[0].avg_spec_accept_length`，内部同时存在日志区间与 lifetime 接受计数。旧实验没有记录每个计时区间的计数边界，因此不能把这些数值视为各个 case 独立的接受长度，更不能据此排除接受情况发生变化。`accept_length` 是平均每轮提交长度，包含非草稿输出 token，不等于草稿接受率。

当前待验证的主假设是：

> 低并发时，MTP 通过一次目标模型验证提交多个有效 token，减少了逐 token decode 的固定成本；并发升高后，批处理、目标模型验证、TP 通信或调度成本成为主导，因此即使平均接受长度相近，MTP 的净收益也会下降。

第一候选改进假设是：

> MTP 的最佳推测步数取决于当前 decode batch size。低批量保持较深推测，高批量减少推测步数，必要时退化为普通解码，可以恢复一部分高并发净收益。

这项候选改进优先使用 SGLang 现有的 adaptive speculation 接口验证，明确定位为当前模型和硬件上的配置与效果评估，不宣称提出新的自适应算法。只有时间线和对照结果显示批量相关的推测开销确实存在，才进入策略实现；如果通信或其他阶段占主导，改进方向改为对应瓶颈。

## 范围和固定条件

研究固定在已有可复现实验环境内：

- 模型：`deepseek-ai/DeepSeek-V4-Flash`；revision `60d8d70770c6776ff598c94bb586a859a38244f1`；
- 远端目录：`$HOME/infra-deepseek-v4`；
- 框架：SGLang 0.5.23；
- 权重执行后端：`flashinfer_mxfp4`；
- GPU：只使用物理 GPU 0、1、2、3，并继续通过 UUID 校验；
- 并行：第一阶段保持 TP=4；不把 TP=2、副本并行或其他机器混入 MTP 归因实验；
- 服务：绑定 `127.0.0.1`，单次只运行当前项目记录的服务；
- 采样：配对 case 使用相同随机种子、请求清单、tokenizer 和采样参数；不通过放宽接受阈值、更改精度或减少输出获得加速；
- 缓存：保持当前关闭 radix cache 的设置，避免前缀复用改变对照；
- 预热：每个配置单独完成预热，预热和首次编译不计入稳态吞吐；
- 结果：保存原始 JSONL、服务日志、版本信息、显存记录和 profiler 文件。

第一阶段不涉及模型权重修改、驱动修改、其他用户进程、未经授权的 GPU、跨机器比较或完整模型质量评测。

## 实验设计

### 1. 性能边界筛选

先使用三类工作负载，区分 prefill 占比和 decode 占比：

| 工作负载标签 | 输入 token | 输出 token | 目的 |
|---|---:|---:|---|
| `short` | 512 | 128 | 与已有结果直接对照 |
| `long-context` | 2048 | 256 | 观察 prefill 变长后 MTP 收益变化 |
| `long-decode` | 512 | 512 | 放大 decode 阶段，观察 MTP 收益能否持续 |

首轮筛选并发度为 1、8、32；每个工作负载分别测试普通解码和当前固定 MTP 配置，即 EAGLE、3 steps、top-k=1、4 draft tokens。每个配置至少重复三轮。

为复现旧结果，先保留原负载和独立预热；正式计时每组请求数不少于 `max(32, 5 × 并发度)`，并通过独立 pilot 为配对配置选择相同请求数，使较快配置的计时区间也达到约 30 秒。未达到时记录实际持续时间并增加两个配置共同使用的请求数，pilot 不混入正式均值。先以三轮发现边界；对约 5% 的小幅变化至少增加到五轮独立复核，不把三轮内的请求当成独立实验重复。

轮次间交替普通解码和 MTP 的执行顺序，记录温度、频率、功耗与其他负载，减少时间漂移影响。每个并发值是客户端请求上限，实际 decode batch size 以服务记录或时间线为准。

如果首轮结果表明收益在并发 8 和 32 之间发生转折，先在相同工作负载补测并发 16；并发 2、4 用于低并发边界，按观察到的空白补测。补测前不更换模型、后端、GPU 数量或缓存策略。

`long-context` 同时改变输入与输出长度，单凭它和 `short` 的差值不能独立归因 prefill。需要解释输入长度效应时，补测 2048/128 作为桥接对照，与 512/128 配对。固定长度测试沿用受控提示集；报告的边界限定于该提示集，不外推为所有真实任务的边界。

每一组结果必须同时保存：

- 成功请求数和失败数；
- 实际输入、输出 token 总数；
- output tok/s；
- TTFT、TPOT、E2E latency、P50/P95/P99 和 ITL；
- `accept_length` 的统计窗口、可获得的 accept rate、正确 draft 计数和验证轮数；优先请求级元数据或计时前后原始计数差，不对两个累计平均值直接相减；无法取得时明确标为服务累计统计；
- GPU 显存、利用率和服务启动参数。

### 2. 时间线剖析

从筛选矩阵中选择三个代表点做短时间 profiler：

- `short`、并发 1、普通解码与 MTP；
- `short`、并发 32、普通解码与 MTP；
- `long-context`、并发 8、普通解码与 MTP。

优先使用远端现有的 Nsight Systems 和 SGLang profiling 接口。SGLang 当前源码已经提供 `draft`、`verify`、`draft_extend` 阶段标记，以及按阶段保存 profile 的请求结构。采集窗口只覆盖预热后的稳定请求，避免把模型加载和首次编译混入时间线。

Profiler 结果需要尽量识别：

- prefill、draft、verify、draft_extend 的阶段范围；
- CUDA kernel 和 CUDA stream 空闲区间；
- NCCL 或其他跨卡通信 kernel；
- scheduler CPU 调度和 GPU 等待之间的间隔；
- detokenization、HTTP 和其他服务层开销。

先以一个短窗口确认四个 TP rank 均有有效 GPU 事件和阶段标记，再扩展到六个配置。Nsight 必须采集服务及其工作进程；只对 HTTP 压测客户端运行 profiler 不能作为服务端 GPU 证据。当前 CUDA Graph 设置保持一致；若为定位源码而关闭 graph，另建诊断 case，不把它作为原配置的性能结论。

Nsight Systems 的原始 GPU 时间线作为直接证据，但 CPU 范围结束不代表异步 GPU 工作结束。按 stream 与 correlation 对应阶段，只有 NVTX 或函数名时不直接当作 GPU 阶段计时。PyTorch Profiler 是后备工具；某工具无法采集时保留诊断日志，不以“已安装”替代“成功采集”。

### 3. 统计和归因

报告以请求级和系统级两个层次呈现结果。

请求级使用同一客户端时钟记录请求发出、首个输出事件与请求完成；流式 TTFT 不直接等同于 prefill，因为还含排队、tokenizer 和服务开销。流式 chunk 可能包含多个 token，ITL 不等于单个 token 的 GPU 计算时间。

```text
客户端 E2E = 首个输出事件前耗时 + 首个输出事件至请求完成耗时
```

系统级采用两层观察，而非相加的时间公式：

- 执行阶段：prefill、draft、verify、draft_extend、阶段外开销；
- 阶段内部活动：计算、通信、内存操作，以及无法解释的间隙。

通信可能位于多个阶段内部，多个 stream 和 TP rank 也可能重叠。分别报告每个 rank 的阶段 wall time、GPU busy 时间并集、通信活动并集、通信与计算重叠，以及未分类区间；不得把四个 rank 的 kernel 总和除以单请求延迟，也不得将通信再次加到已经包含它的阶段时长上。只有可靠的 stream 关联或受控对照才能估计暴露在关键路径上的通信；GPU idle 仅是观察，不能全部称为调度瓶颈。

报告必须把结论分成三类：

1. **直接测得**：原始 benchmark 指标、服务内部统计、profiler 阶段和 kernel 时间；
2. **对照推断**：普通解码与 MTP 的差值、不同并发和上下文下的变化；
3. **尚未能归因**：时间线无法独立区分的通信、调度或框架开销。

如果某个阶段没有可靠的独立计时，不报告虚假的百分比分解。

### 4. 第一个改进验证

在性能边界和时间线分析完成后，验证一个批量相关的自适应 MTP 策略：

```text
小 batch：3 steps
中等 batch：2 steps
较大 batch：1 step
零步路径：仅在已安装版本明确支持后另列诊断对照；始终保留真正的非 MTP 基线
```

先对代表性并发测试固定 1、2、3 步，top-k=1 时对应验证容量 2、3、4；这属于同一推测深度参数族，不把验证容量当成独立变量。由这些结果确定批量区间，再与现有 adaptive 功能比较。使用自定义配置限制候选层级为 1、2、3，避免通用默认值引入未计划的更深图捕获和显存消耗。

具体 batch 边界在筛选数据上确定后冻结；新的轮次与未用于拟合的请求用来验证收益，避免同一批数据同时用于选策略和宣称改进。除固定并发外增加 1→32→8 的变负载回放，记录真实 batch、活跃步数、切换次数与切换开销。

在线文档与已安装实现的约束不同：2026-10-30 源码预检确认本安装版解析器允许零步，默认配置也含零步。本研究仍将候选集合限制为1、2、3，零步只作为需单独验证的诊断路径，不纳入默认候选集合。即使底层存在零步分支，也可能保留 draft KV 更新等开销，不能当作关闭 MTP。若当前安装接口无法支持候选配置，记录不支持及日志，改用固定深度对照验证假设，不在未审查前修改框架核心。

改进对照至少包含：

- 当前固定 3-step MTP；
- 该场景筛选出的最佳固定深度 MTP；
- 使用冻结配置的自适应 MTP；
- 真正关闭 MTP 的普通解码。

候选改进只有同时满足以下条件才写成有效改进：

- 相同输入输出长度、并发、模型、GPU、缓存和随机条件；
- 至少三轮重复；
- 错误数为零，实际 token 数一致；
- 吞吐提升超过独立重复测量波动，单列逐轮结果和区间，不把请求级样本冒充独立重复；以约 5% 作为需要五轮复核的暂定保留门槛；
- 相对固定 3-step 的 TTFT 与 P99 恶化各不超过 5%，并同时披露与最佳固定深度及普通解码的比较；小样本 P99 标为描述性数据，若尾延迟决定是否保留策略，应增加样本至至少 1000 个请求并复核；
- 在约定的无 profiler 验收负载中确认收益；冻结模型、采样与接受阈值后进行独立正确性冒烟检查，异常或新增错误不得被吞吐掩盖。

如果自适应 MTP 没有达到门槛，报告将保留负结果，并根据时间线选择通信、调度或算子方向作为下一阶段候选。

## 风险和处理

- Nsight Systems 会引入测量扰动：只对短窗口和代表点采集，不用 profiler 吞吐替代基准吞吐；
- 内部 accept 统计可能按服务区间累积或重置：每个 case 记录服务统计边界，必要时按 case 重启服务；
- MTP 自适应策略可能依赖当前 SGLang 版本的隐藏配置：先审计现有接口，再决定配置包装或最小代码改动；
- 高并发下的通信和调度可能无法从单条时间线完全分离：报告保留组合开销标签，不强行归因；
- 远端当前已有最终服务：实验启动前检查 `active-server.json`、进程、健康接口和显存，停止时只使用项目范围内的 `stop.py`。
